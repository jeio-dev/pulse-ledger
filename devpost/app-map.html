PulseLedger Architecture & Code Guide

Single-screen plain-English cashflow parser & real-time What-If expense simulator.

Snapshot commit: eb92df4
Stack: Next.js 15 · React 19 · TS · Tailwind · Zod

1. Plain-Language Overview

PulseLedger turns a messy monthly cashflow paragraph into three structured expense buckets (Fixed Essentials, Flexible Living, and Discretionary Wants), calculates 30-day Safe Daily Allowance vs. Actual Daily Spend, and lets users drag 0%–150% What-If sliders on non-fixed expenses to watch their daily pace and 1-year projected savings flip from deficit to surplus in real time.

Contract Layer (src/lib/schemas.ts)

Single Zod source of truth (BudgetResponseSchema, BudgetLedgerStateSchema) shared across the API route, fallback parser, localStorage hydration, and React state.

Resilient Parser (src/app/api/parse-budget/route.ts)

Calls OpenRouter with a 6-second timeout when OPENROUTER_API_KEY is set, and automatically falls back to deterministic preset/clause parsing in src/lib/fallback-parser.ts.

Zero-Latency Math (src/lib/calculations.ts)

Enforces locked 100% essentials via computeSimulatedAmount and derives 30-day daily burn, largest leak, and traffic-light badges via computeDerivedMetrics.

Interactive Workspace (src/app/page.tsx)

Coordinates left-column input, right-column KPI cards, stacked proportion bar, slider ledger, 5-part Markdown export, and localStorage["pulse_ledger_state"] sync.

3. Three-Stop Code Reference Route

Use this reference route to trace the contract between Zod schemas, normalization math, and interactive UI:

Stop 1 — The Zod Contract & State Shape
Path: src/lib/schemas.ts · Symbols: ExpenseItemSchema, BudgetResponseSchema, BudgetLedgerStateSchema

Defines the three valid categories ("essential" | "flexible" | "want"), the API output contract, and the persisted client state shape.

Stop 2 — Single-Source-of-Truth Normalization & 30-Day Formulas
Path: src/lib/calculations.ts · Symbols: computeSimulatedAmount, normalizeLedgerState, computeDerivedMetrics

Clamps "essential" items to 100% and rounds simulatedAmount in one function used by parsing, slider updates, reset, and storage hydration; computes safeDailyAllowance, simulatedDailySpend, annualizedSavings, and badge statuses.

Stop 3 — Slider Scrubbing & Workspace Persistence
Path: src/app/page.tsx & src/components/CategoryLedger.tsx · Symbols: handleSliderChange, parseSavedLedgerState

Renders locked rows for Fixed Essentials and Radix 0%–150% sliders for adjustable rows, updating React state and syncing localStorage["pulse_ledger_state"] without re-calling the API.

4. “To Change This, Start Here” Pointers

  • Add or edit a preset scenario pill: Open src/lib/presets.ts and edit PRESET_SCENARIOS (each entry holds both the plain-English rawInput and its deterministic fallbackResponse).
  • Adjust traffic-light surplus thresholds or 30-day math: Open src/lib/calculations.ts inside computeDerivedMetrics (currently emerald when surplus >= 10% of income, amber between 0%–10%, and rose below $0).
  • Tune keyword rules for offline/fallback parsing: Open src/lib/fallback-parser.ts and update INCOME_KEYWORDS or EXPENSE_RULES.
  • Change the Slider range or step size: Open src/components/CategoryLedger.tsx (<Slider min={0} max={150} step={5} />) and matching bounds in src/lib/schemas.ts / src/lib/calculations.ts.
  • Customize the copied Markdown template: Open src/lib/markdown-export.ts inside formatActionPlanMarkdown.

5. A Practice to Reuse — Spec-to-Schema-to-Slice Invariant Verification

What happened in this project: During planning (devpost/spec.md > Decisions and Open Issues > Build-Time Scrutiny Items), two boundary risks were explicitly recorded before writing application code:

  • State Normalization Invariant: Storing both sliderPercent and simulatedAmount inside localStorage["pulse_ledger_state"] risked drift if hydrated or updated in multiple places. Routing every state transition through computeSimulatedAmount in src/lib/calculations.ts guaranteed Fixed Essentials stay locked at 100% everywhere.
  • Fallback Clause Separation: Writing a mechanical check for src/lib/fallback-parser.ts in Slice 1 immediately caught that a sentence like "I earn $3,800 a month after tax" matched standalone tax in the expense rules—allowing a targeted fix (property tax) documented in devpost/checklist.md > Revisions before building the dashboard UI.
How to reuse this pattern on your next agent build

Whenever a product rule constrains data (like read-only categories or derived totals), write a named normalization function in the spec's Data Model section and require Slice 1/2 mechanical verification to test an adversarial input against it before moving to downstream UI slices.
